# Fix: Sitemap Lastmod Accuracy — theroofstore.net

## 1. Problem Fixed
All 150+ URLs in `sitemap.xml` (homepage, product pages, blog posts, and every county/city service-area page) currently share the identical `<lastmod>2026-07-28</lastmod>` value. Search engines treat a uniform, non-differentiated lastmod as a low-trust signal and may discount it entirely when deciding which URLs to prioritize for re-crawl — which defeats the purpose of having lastmod at all.

## 2. Recommended Fix
Generate `<lastmod>` per URL from the **actual last-edit timestamp of that specific page's content**, not from a single global site-build date. Three cases, based on what we already confirmed on this site:

| URL type | Correct lastmod source |
|---|---|
| `/roof-coating-florida` | Use the page's own `dateModified` field, which is already correctly set to **2026-07-18** in its Article schema — the sitemap should match this, not overwrite it with the deploy date. |
| Evergreen/static pages (`/about`, `/factory`, `/distributorships`, product pages) | Pull the CMS/database "last updated" timestamp for that record. If these pages haven't changed content in months, their lastmod should reflect that — not today's date. |
| Blog posts | Use each post's real publish/edit date (already tracked in most blog systems as `updated_at` or `published_at`). |
| Templated city/service-area pages | Only bump lastmod for a given city page when that page's own unique content block changes — not on every global template deploy, since that recreates the same false-freshness problem. |

## 3. Config / Implementation Example

**Wrong (current behavior)** — every entry gets the build timestamp:
```xml
<url>
  <loc>https://www.theroofstore.net/roof-coating-florida</loc>
  <lastmod>2026-07-28</lastmod>
  <changefreq>monthly</changefreq>
  <priority>0.9</priority>
</url>
<url>
  <loc>https://www.theroofstore.net/about</loc>
  <lastmod>2026-07-28</lastmod>
  <changefreq>yearly</changefreq>
  <priority>0.8</priority>
</url>
```

**Correct** — lastmod reflects each page's real content edit date:
```xml
<url>
  <loc>https://www.theroofstore.net/roof-coating-florida</loc>
  <lastmod>2026-07-18</lastmod>
  <changefreq>monthly</changefreq>
  <priority>0.9</priority>
</url>
<url>
  <loc>https://www.theroofstore.net/about</loc>
  <lastmod>2025-11-02</lastmod>
  <changefreq>yearly</changefreq>
  <priority>0.8</priority>
</url>
```

**Sitemap generator logic (pseudocode)** — apply this wherever `sitemap.xml` is generated (build script, CMS plugin, or server route):
```
for each page in site_pages:
    lastmod = page.content_updated_at   # from CMS/DB record, NOT datetime.now()
    write_sitemap_entry(page.url, lastmod, page.changefreq, page.priority)
```
If the sitemap is currently generated with a single `build_time` variable applied to every entry, that is the exact line to remove.

## 4. Validation Steps
1. After redeploying, fetch `https://www.theroofstore.net/sitemap.xml` and confirm lastmod values differ across URL groups (e.g., `/roof-coating-florida` shows 2026-07-18, older static pages show older dates).
2. Spot-check 3-4 pages: their sitemap lastmod should match the `dateModified` in that page's own schema (where present).
3. In Google Search Console → Sitemaps, resubmit `sitemap.xml` and monitor whether "Discovered" vs. "Last read" timestamps start moving independently per URL over the following weeks, rather than all updating in lockstep.

## 5. Risk Notes
- Do not "fix" this by setting today's date on next deploy — that just recreates the same false-freshness pattern once more. The date must come from real content-edit tracking going forward.
- If the sitemap is auto-generated by a static-site build process with no per-page timestamp tracking, this requires adding that tracking at the CMS/data layer first — flag this as a dependency if the current system has no such field.
- This fix is config/data-layer work on the site's own generator, not something pushable through a connected storefront platform in this session — implementation needs to happen in the site's CMS or build pipeline.
